Why Multiobjective Optimization?
Real-world problems rarely have just one goal
● Real design and decision problems involve several competing goals at 
once, not one:
– Car design — minimize cost, maximize mileage, maximize safety
– Investment portfolio — maximize return, minimize risk
– 5G network planning — maximize bandwidth, minimize latency, minimize 
energy
● The core difficulty: conflict — improving one objective typically worsens 
another.
● Single-objective tools (Simplex, GA, PSO) return one point — they cannot 
represent a trade-off.
● Multiobjective Optimization instead returns a whole set of trade-off 
solutions for a human decision-maker to choose from. 0

SECTION 1 · BASICS OF MOO
The Mathematical Formulation
General vector-optimization form of a multiobjective problem
min F(x) = [ f1(x), f2(x), ... , fk(x) ]T
subject to:   gi(x) ≤ 0 ,      hj(x) = 0
Notation used throughout this chapter
● x = (x₁, x₂, …, xₙ) — the decision variable vector (what we control)
● F(x) — the objective vector; each fᵢ(x) is one objective function
● k ≥ 2 — number of objectives (this is what makes it "multi")
● gᵢ(x) ≤ 0 — inequality constraints on the design
● hⱼ(x) = 0 — equality constraints on the design
● Key consequence: with k ≥ 2 conflicting goals, there is no single "best" x* — we instead 
seek the Pareto-optimal set.
F(x)
f₁(x)  — minimize cost
f₂(x)  — maximize mileage
f₃(x)  — maximize safety
A vector-valued objective function maps one design x to several 
simultaneous outcomes.

Pareto Dominance: When Is One Solution Better?
The rule that lets us compare solutions without collapsing objectives into one number
A ≺ B  ⟺  fi(A) ≤ fi(B)  ∀i,   and   fj(A) < fj(B)  ∃j
● Solution A dominates solution B (written A ≺ B) when, for minimization:
– A is no worse than B in every objective
– A is strictly better than B in at least one objective
● A solution is non-dominated if no other feasible solution dominates it.
● Dominance gives a partial order — not every pair of solutions is comparable, 
which is exactly why a Pareto front (a set), not a single point, is the outcome of 
MOO.

Pareto Optimal Set and Pareto Front
The goal of every MOO algorithm, stated precisely
● Pareto Optimal Set
– All non-dominated solutions in decision space (the x's).
● Pareto Front
– The image of that set in objective space (the F(x) values) — what 
we actually plot.
● Goal of MOO
– Find solutions that are both close to the true front and well 
spread along it.
● Convergence
– How close the obtained solutions are to the true Pareto front.
● Diversity
– How evenly the obtained solutions are spread along the front.

Pareto Dominance with Mixed Objectives
Handling simultaneous minimize + maximize goals
● Real problems mix directions, e.g. Min Cost (f₁) and Max Mileage (f₂).
● Standard trick: convert every maximize objective to minimize.
– Max f₂  ≡  Min (−f₂)
● Mixed dominance rule — A dominates B if:
– f₁(A) ≤ f₁(B)   (A is no more expensive)
– f₂(A) ≥ f₂(B)   (A gives no worse mileage)
– and at least one of these is a strict inequality.

Step 1: Define Decision Variables
The quantities we are actually allowed to change
x = (x1, x2, … , xn)     bounds:  xi ∈ [xiL, xiU]
Worked example — Car Design
● x₁ : Engine size, range 1.0 – 3.0 litres
● x₂ : Safety-feature level, range 1 – 5
● x₃ : Material quality grade, range 1 – 3
● These three numbers fully describe one candidate car design; 
every objective and constraint in the rest of this example is 
written purely in terms of x₁, x₂, x₃.
Required vs. free variables
● n = 3 — dimensionality of the decision space (fixed by the designer)
● x₁, x₂, x₃ — the free (random / searchable) variables an algorithm perturbs
● xᵢᴸ, xᵢᵁ — required bounds; every algorithm in this chapter needs these to 
generate or clip feasible x
● These bounds later become the initialization range in Step 5 (e.g. NSGA-II's 
random population).

Step 2: Define Objective Functions
What each design is judged by, and in which direction
F(x) = [ f1(x), … , fk(x) ]T
Worked example — Car Design
● f₁ : Cost  →  Minimize
● f₂ : Mileage  →  Maximize

● Conversion for a uniform minimization framework:
– Minimize   f₁,  −f₂,  −f₃
Required variables
● k = 3 — number of objectives
● f₁(x), f₂(x), f₃(x) — objective functions, each computed from x₁, x₂, x₃
● Direction flags (min/max) per objective — required before any dominance check 
can run (see Slide 7)
● Every later method (weighted sum, ε-constraint, NSGA-II's sorting…) consumes 
exactly this vector F(x).

Step 7: Rank Solutions (Non-Dominated Sorting)
Layering the population into fronts of decreasing quality
● For every solution p, count:
– nₚ — number of solutions that dominate p
– Sₚ — the set of solutions p dominates
● If nₚ = 0 → p belongs to Front 1 (the current non-dominated set).
● For each q ∈ Sₚ, decrement n_q by 1; if n_q becomes 0, q joins the next 
front.
● Repeat until every solution is assigned to a front.
● This assumes every solution is feasible — the next slide covers what 
changes when some aren't.

SECTION 2 · 10 -STEP MOO PROCEDURE
Comparing Solutions Under Constraints
Deb's rule — extending dominance so infeasible solutions never sneak into the front
● The dominance rule from Slide 5 only compares objective values — it has 
no notion of whether a solution is even feasible.
● Deb's constrained-dominance rule extends it with three cases, checked in 
order:
● Rule 1 — Feasible beats infeasible, always.
– A feasible solution dominates any infeasible one, no matter how good 
the infeasible one's objectives look.
● Rule 2 — Feasible vs. feasible.
– Use ordinary Pareto dominance (Slide 5) on the objectives.
● Rule 3 — Infeasible vs. infeasible.
– The solution with the smaller total constraint violation dominates —
objectives are ignored entirely.
CV(x) = Σ max(0, gi(x)) + Σ | hj(x) |
Solution Feasible? Violation f₁ f₂
A Yes 0 3 6
D Yes 0 4 5
B No 2 1 2
C No 5 0.5 1
Applying the rules
● A, D dominate B, C (Rule 1) — regardless of B, C's objective values.
● A vs. D (Rule 2): neither dominates — a genuine trade-off (3<4 but 6>5).
● B vs. C (Rule 3): violation 2 < 5, so B dominates C — even though C's 
objectives (0.5, 1) look better than B's (1, 2).

Step 8: Preserve Diversity (Crowding Distance)
Rewarding solutions that sit in sparsely populated parts of the front
di = Σm | fm(i+1) − fm(i−1) | ⁄  fmmax − fmmin
● First sort the front's solutions by each objective in turn — "i−1" and "i+1" 
mean a solution's neighbors in that sorted order, not its neighbors in the 
population list.
● Boundary solutions (first/last on a front) get d = ∞ — they are always 
kept.
● Higher d means better diversity — the point has more "elbow room" from 
its neighbors.

Why elitism is essential

SECTION 3 · CLASSICAL METHODS
Before the Methods: Convex vs. Non-Convex Fronts
The one shape distinction that decides which classical method will actually work
● A front is convex when every point on it sits on the outer edge of the 
point cloud — a straight line between any two front points never cuts 
inside the front.
● A front is non-convex when part of it "dents" inward — some non-
dominated points sit behind the straight line joining their neighbors.
● Why it matters:
– Weighted Sum only ever finds points on the outer straight-line 
boundary (the convex hull) of the front.
– A dented, non-convex point can never win for ANY choice of weights 
— no matter how they're tuned — so Weighted Sum silently skips it.
– ε-Constraint, Benson's, and the Tchebycheff (p→∞) Weight Metric 
don't have this blind spot — they can reach into the dent.

SECTION 3 · CLASSICAL METHODS
Weighted Sum Method
Combine every objective into one scalar using fixed weights
F(x) = Σi=1k wi fi(x)      ,      Σwi = 1 , wi ≥ 0
Algorithm Steps
● 1. Choose weights w₁, …, wₖ that reflect relative importance.
● 2. Solve the resulting single-objective problem for x*.
● 3. Vary the weights and re-solve to trace out multiple Pareto points.
Parameters & When to Use
● Parameters: weights wᵢ
● Complexity: same as one single-objective solve
● Best used when: the true Pareto front is convex and preferences are roughly 
known
● Avoid when: the front is non-convex — whole regions become unreachable
✓ Advantages
● Simple to implement
● Fast — one optimization call per weight set
● Works with any single-objective optimizer
✗ Disadvantages
● Cannot find solutions in non-convex regions of the front
● Requires meaningful weights up front
● Very sensitive to the relative scaling of objectives

SECTION 3 · CLASSICAL METHODS
Real-Life Problem: Manufacturing Trade-off
Weighted Sum Method
Scenario
● A factory wants to minimize production cost (f₁) while 
maximizing product quality (f₂).
● Decision variable: x = production speed, ranging 1–10.
F(x) = w1(x−3)2 + w2(x−7)2
Variables in this problem
● x — production speed (decision variable), 1 ≤ x ≤ 10
● f₁(x) = (x − 3)² — cost, minimized when speed is near 3
● f₂(x) = (x − 7)² — treated as minimize(−quality), so quality peaks near speed 7
● w₁, w₂ — required weights, with w₁ + w₂ = 1

ε-Constraint Method
Optimize one primary objective; turn the rest into constraints
min f1(x)      s.t.      fi(x) ≤ εi ,  i = 2, …, k
Algorithm Steps
● 1. Choose the primary objective f₁ to optimize directly.
● 2. Fix ε values (upper bounds) for every other objective.
● 3. Solve the constrained single-objective problem.
● 4. Vary εᵢ and re-solve to sweep out the front.
Parameters & When to Use
● Parameters: εᵢ bound for each secondary objective
● Complexity: k × one single-objective solve
● Best used when: the front is non-convex and one objective has clear priority
● Avoid when: there are many objectives — tuning many εᵢ values becomes 
unwieldy
✓ Advantages
● Finds solutions in non-convex regions unreachable by weighted sum
● Gives precise, interpretable control per objective
✗ Disadvantages
● Needs careful tuning of ε for each secondary objective
● Requires many separate optimization runs

Benson's Method
Maximize weighted "distance past target", summed across objectives
max Σ λi si(x)      s.t.  si(x) ≥ 0
Algorithm Steps
● 1. Choose a reference point z* — one target value per objective, in 
that objective's own original units.
● 2. Define sᵢ = (target − value) if objective i is minimized, or (value − 
target) if maximized — always "how far past target, in the good 
direction".
● 3. Choose direction weights λᵢ.
● 4. Maximize Σλᵢsᵢ(x), subject to sᵢ(x) ≥ 0 for every i, and solve for x*.
Parameters & When to Use
● Parameters: reference point z*, weights λᵢ
● Complexity: one constrained solve per (z*, λ) pair
● Best used when: a meaningful reference point is available and the front may be 
non-convex
● Avoid when: no sensible reference point can be defined
✓ Advantages
● Can locate non-convex Pareto regions
● Reference point gives an intuitive anchor for the search
✗ Disadvantages
● Requires choosing a reference point
● Still needs weights, so preferences must be at least partly known

Real-Life Problem: Hospital Resource Allocation
Benson's Method — problem and solution together
Scenario
● A hospital wants to minimize operating cost (f₁) while 
maximizing patients treated (f₂).
● Reference point z* = (100, 50) — a cost target of 100 and a 
patients target of 50.  Weights: λ₁ = λ₂ = 0.5.
● Achievements: s₁(x) = 100 − f₁(x)   (cost is minimized, so "past 
target" means below it) s₂(x) = f₂(x) − 50   (patients is 
maximized, so "past target" means above it)
● Solve:  maximize  0.5·s₁ + 0.5·s₂ = 0.5(100 − f₁) + 0.5(f₂ − 50)   
subject to  s₁ ≥ 0 (f₁ ≤ 100) and s₂ ≥ 0 (f₂ ≥ 50).
● Result: the optimizer pushes cost as far below 100, and 
patients as far above 50, as feasibility allows — tracing a non-
dominated point on the front for this (z*, λ) choice.
Variables in this problem
● z₁* = 100 — reference cost target (a min-type objective, so s₁ = target − value)
● z₂* = 50 — reference patients-treated target (a max-type objective, so s₂ = value − 
target)
● λ₁ = λ₂ = 0.5 — equal-priority direction weights
● Re-running with different λ gives different points along the Pareto front.

Weight Metric Methods
Minimize a weighted distance to an ideal point, using a p-norm
min ( Σ wi | fi(x) − zi* |p )1/p
Algorithm Steps
● 1. Choose the ideal point z* (the best achievable value of each 
objective alone).
● 2. Choose the norm order: p = 1 (Manhattan), p = 2 (Euclidean), p 
→ ∞ (Tchebycheff).
● 3. Choose weights wᵢ and minimize the resulting distance.
Parameters & When to Use
● Parameters: weights wᵢ, norm order p, ideal point z*
● Complexity: one solve per (p, w, z*) combination
● Best used when: fine control over the shape of the trade-off is needed
● Avoid when: the ideal point z* is not known or expensive to estimate
✓ Advantages
● Flexible — the p-norm choice reshapes what gets found
● As p → ∞ (Tchebycheff), non-convex regions become reachable
✗ Disadvantages
● Needs an ideal point z*, which itself requires k extra single-objective solves
● Solution is sensitive to the choice of p

Value Function Method
Optimize the decision-maker's own utility function directly
max  v( f1(x), f2(x), … , fk(x) )
Algorithm Steps
● 1. Elicit the decision-maker's value function v(·) — how they trade 
off objectives.
● 2. Substitute F(x) into v and solve as a single-objective problem.
● 3. The resulting x* is the decision-maker's most-preferred point on 
the front — no further ranking needed.
Parameters & When to Use
● Parameters: the value function v(·) itself
● Complexity: one single-objective solve, given v
● Best used when: the decision-maker can articulate a believable trade-off function
● Avoid when: preferences are unknown, unstable, or hard to elicit reliably
✓ Advantages
● Theoretically the most correct result — it directly optimizes what the decision-
maker actually values
● Skips the need to generate and then rank a whole front
✗ Disadvantages
● v(·) is very rarely known precisely in practice
● Eliciting an accurate value function from a human is difficult and error-prone

Goal Programming
Set numeric targets and minimize how far you fall from them
min Σ (di⁺ + di⁻)      s.t.  fi(x) + di⁻ − di⁺ = Ti
Algorithm Steps
● 1. Set a target Tᵢ for every objective.
● 2. Introduce deviation variables dᵢ⁺ (overshoot) and dᵢ⁻ (undershoot) 
per objective.
● 3. Minimize the total deviation, subject to the target equation for 
each objective.
Parameters & When to Use
● Parameters: targets Tᵢ, deviation weights
● Complexity: one linear/nonlinear program
● Best used when: the decision-maker can state clear numeric targets for each goal
● Avoid when: no sensible targets exist, or the targets make the problem infeasible
✓ Advantages
● Very intuitive — thinking in "targets" matches how people naturally set goals
● Naturally handles many goals at once, even with different units
✗ Disadvantages
● Requires meaningful targets Tᵢ to be set in advance
● A poorly chosen target set can make the problem infeasible

VIKOR: Compromise Ranking
VIseKriterijumska Optimizacija I Kompromisno Resenje
Algorithm Steps
● 1. Compute Sᵢ (group utility) and Rᵢ (individual regret) per solution.
● 2. Combine them into Qᵢ using the trade-off parameter v.
● 3. Rank solutions by Qᵢ — lowest is the best compromise.
Qi = v (Si − S*)/(S⁻ − S*) + (1−v) (Ri − R*)/(R⁻ − R*)
✓ Advantages
● Balances group utility and 
individual regret
● Gives a well-defined 
compromise, even with 
conflicting criteria
✗ Disadvantages
● Requires choosing v (the 
utility/regret trade-off 
weight)
● More computation than a 
plain ranking method

A 0.30 0.15 0.00 1

● v = 0.5 gives equal weight to overall utility and worst-case regret.
● Solution A has both the lowest utility gap and lowest regret ⟹ Qₐ = 0.00, the best 
compromise.
● Unlike TOPSIS, VIKOR explicitly protects against a solution that is excellent on 
average but very poor on one criterion (high regret).

Summary of Part 1
The essentials to carry forward into Part 2
● MOO deals with conflicting objectives — the answer is a Pareto front, not one point.
● Pareto dominance gives the comparison rule; mixed min/max problems convert to all-minimize first.
● The 10-step procedure (variables → objectives → constraints → algorithm → … → output) is the same skeleton behind every method in this 
chapter, classical or evolutionary.
● Classical methods (weighted sum, ε-constraint, Benson's, weight metric, value function, goal programming, lexicographic) each turn the 
multiobjective problem into one or more single-objective problems.
● TOPSIS and VIKOR don't generate solutions — they rank a front you already have.
● Choosing convex vs. non-convex-capable methods, and matching complexity to your objective count, are the two decisions that matter 
most in practice.
